# 降價追蹤器

追蹤 91app（NineYi）平台商店的商品，一變便宜就寄 email 給你。

目前追的是 HOME SHOP 的「【初秋新品】HS 後鬆緊都會長裙 墨灰色」。

## 為什麼不能只看價格

這很重要，不然你會以為程式壞了：**商品頁上的 `Price` 欄位永遠是 2,190，不會因為打折而變動。**
79 折是掛在「促銷活動」清單裡的一檔活動（`【春夏單品】單件79折`），而且折扣率只寫在活動**名稱**裡，
API 不會給你折後數字。

所以這支程式做兩件事：

1. 讀出原價（`SuggestPrice` / `Price`）
2. 讀出進行中的活動清單，從名稱裡解析出「單件就能用」的折扣率，算出實際要付多少

滿額、滿件的活動（例如「滿額現折」「第二件5折」）不列入計算，因為單買一件吃不到，
但還是會列在信裡供參考。

## 安裝

不需要任何套件，Python 3.11 以上即可（只用標準函式庫）。

```bash
python -m tracker --dry-run   # 查一次並印出，不寄信也不寫檔
```

輸出長這樣：

```
【初秋新品】HS 後鬆緊都會長裙 墨灰色
  定價 NT$2,190 / 售價 NT$2,190 / 實付 NT$1,730（約 79折）
    【官網限定】雙11預購會，滿額現折再送券（需湊滿額），至 2026-11-04
  * 【春夏單品】單件79折（79折），至 2026-10-31
    加購限定優惠款，至 2026-10-31
```

`*` 標的那檔就是目前算進實付價的折扣。

## 設定要追什麼

編輯 `config.json`：

```json
{
  "watches": [
    {
      "id": "homeshop-11207741",
      "label": "【初秋新品】HS 後鬆緊都會長裙 墨灰色",
      "url": "https://bmai.app/2b776daf",
      "target_price": null
    }
  ]
}
```

- `url` 可以直接貼 bmai.app 的短網址，程式會自己解出真正的商品頁
- `target_price`：設成數字（例如 `1500`）就只有降到這個價以下才寄信；留 `null` 的話只要有降就寄
- 要追更多商品就在 `watches` 裡多加幾個，`id` 不要重複

想「再等折扣多些」的話，把 `target_price` 設在現在的 1,730 以下，例如 `1500`（約 68 折）。

## 設定信箱

用環境變數，不要寫進檔案：

| 變數 | 說明 |
| --- | --- |
| `SMTP_HOST` | 例如 `smtp.gmail.com` |
| `SMTP_PORT` | 預設 `587`；填 `465` 會自動改用 SSL |
| `SMTP_USER` | SMTP 帳號 |
| `SMTP_PASS` | SMTP 密碼。**Gmail 要用「應用程式密碼」，不是你的登入密碼** |
| `MAIL_FROM` | 寄件人，省略的話就用 `SMTP_USER` |
| `MAIL_TO` | 收件人，多個用逗號分隔 |

Gmail 的應用程式密碼要先開兩步驟驗證，再到 Google 帳戶 → 安全性 → 應用程式密碼 產生一組 16 碼。

測一下信箱通不通：

```bash
export SMTP_HOST=smtp.gmail.com SMTP_USER=你的@gmail.com SMTP_PASS=應用程式密碼 MAIL_TO=你的@gmail.com
python -m tracker --force
```

## 排程執行

### 由 Claude 的排程任務執行（目前實際在跑的方式）

Claude 的定時任務每天台灣時間 08:53、13:53、18:53 各開一個新 session，
匿名 clone 這個 repo、執行 `python -m tracker --no-email`，有降價就由 Claude
直接推播＋寄信。**不需要 SMTP 設定、不需要應用程式密碼、不需要任何憑證。**

`--no-email` 會照常查詢，該通知時在最後印出 `NOTIFY:` 開頭的一行，
沒事則印 `NOTIFY: none`，方便排程的 session 判斷。

```bash
python -m tracker --no-email
```

#### 重要：基準是固定的

排程刻意**不把狀態推回 repo**（觸發出來的 session 沒有推送權限，
而取得推送權限需要憑證，不值得為了追蹤一件裙子而承擔那個風險）。

所以 `state.json` 裡的 `effective` 是一個**人工維護的固定基準**，
每次執行都拿它來比對。後果是：

- 價格降下去之後，**每次執行都會再通知一次**（一天三次），直到基準被人工更新
- 這是刻意的取捨：寧可吵，也不要靜默失效

降價收到通知、也下手之後，把 `config.json` 的 `target_price` 設低一點，
或直接更新 `state.json` 裡的 `effective`，重複通知就會停。

要讓狀態自動累積的話，用下面的 GitHub Actions，它有 repo 的寫入權限，
不需要額外憑證。

### GitHub Actions（不用設信箱，推薦）

`.github/workflows/track.yml` 每小時查一次，有降價就在這個 repo 開一張 issue 並 @ 你，
GitHub 會寄信、也會推播到 GitHub App。查價失敗時那次執行會失敗，GitHub 也會寄失敗通知信。
每次查完會把 `state.json` commit 回 repo，當作下次比價的基準。

到 Actions 頁手動按 Run workflow 並勾 `force`，就會開一張測試 issue，確認收得到通知。

### 自己用 SMTP 寄信

#### 自己的機器

```cron
17 * * * * cd /path/to/repo && /usr/bin/python3 -m tracker >> tracker.log 2>&1
```

## 通知規則

會寄信的情況只有兩種：

1. **實付價比上次低。**（設了 `target_price` 的話還要降到目標價以下）
2. **出現算不出折扣的新活動。** 例如店家把活動取名成「限時優惠」，名稱裡沒有折數，
   程式算不出實付價。這時會寄信請你自己去看一眼，寧可多問一句也不要整檔活動錯過。

不會寄信的情況：第一次執行（只記錄基準）、價格沒變、價格變貴、
已經通知過的同一檔活動、折價券異動。

折價券之所以不觸發通知，是因為店家常年掛著生日禮、開卡禮這類會員券，
而且名稱帶年月（`202610`）每個月都會變，拿來當通知條件只會每月誤報一次。
券只在信裡列出來供參考，而且只列這個價位用得到的（門檻高於實付價的會濾掉）。

## 這個程式抓不到什麼

說在前面，**它沒辦法保證抓到每一次降價**。已知的漏洞：

| 漏的情況 | 說明 |
| --- | --- |
| 快閃特價 | 每小時查一次，比這更短的特價會錯過 |
| 會員等級限定價 | 未登入抓不到，程式沒有你的帳號 |
| App 限定優惠 | 只出現在 App 裡，網頁版看不到 |
| 排程延遲 | GitHub Actions 的排程是盡力而為，尖峰時段可能延遲數十分鐘 |
| 沒寫折數的活動 | 算不出實付價，但會寄信叫你自己看（見上面的通知規則第 2 點） |

前三項是資料來源本身的限制，除非登入或裝 App，否則補不起來。

排程還有一個陷阱：**GitHub 會在 repo 連續 60 天沒有新 commit 時自動停用排程。**
所以程式每週會在 `state.json` 寫一次心跳值，確保至少每週產生一次 commit 把排程續命。

每小時跑一次、每次約一分鐘，一個月約 720 分鐘。公開 repo 不計費；
私有 repo 的免費額度是每月 2,000 分鐘，也夠用。

## 檔案

```
tracker/discount.py   把「單件79折」這種活動名稱解析成 0.79，算出實付價
tracker/source.py     抓商品頁、解析內嵌的 JSON（含 bmai.app 短網址還原）
tracker/notify.py     組信並用 SMTP 寄出
tracker/state.py      上次的價格紀錄
tracker/__main__.py   指令列進入點與通知判斷
config.json           要追蹤的商品
state.json            自動產生的價格紀錄，不要手動改
```

## 已知限制

- 折扣率是從活動名稱的中文解析出來的，沒有數字就算不出來（但會寄信請你自己看）。
- 滿額、滿件的折扣不列入實付價計算，因為單買一件吃不到。
- 折價券不會自動算進實付價，因為要自己去領、而且各有使用門檻。
- 只支援 91app / NineYi 平台的商店頁（`*/SalePage/Index/*`）。
